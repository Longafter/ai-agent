# 🚀 企业级 Git 工作流与代码提交规范

在处理任何代码改动和提交（git commit）时，必须**严格遵守**以下规范。

## 1. 规范化提交格式 (Conventional Commits)

Commit Message 必须按照以下标准格式编写，绝不允许随意乱写：
`<type>(<scope>): <subject>`

### 允许的 `<type>`：
- `feat`: 新增功能 (feature)
- `fix`: 修复缺陷 (bug)
- `docs`: 文档变更 (documentation)
- `style`: 代码格式优化（如空格、缩进调整，不影响业务逻辑）
- `refactor`: 代码重构（不增加新功能，也不修复 bug）
- `perf`: 性能优化
- `test`: 增加或修改测试用例
- `chore`: 构建、依赖或辅助相关的杂项变动
- `revert`: 代码回退

### `<scope>` (影响范围)
如果有明确的作用域，请带上 `(<scope>)`，例如：`(auth)`, `(ui)`, `(db)`, `(api)` 等。若是全局修改则可以省略。

### `<subject>` (简述)
用一句话简明扼要地描述改动内容，必须符合如下规则：
- **强烈要求**：用简洁的中文叙述。
- **排版要求**：如果是动宾结构，使用祈使句（如：“新增用户登录接口” 而不是 “新增了用户登录接口”）。
- **标点要求**：结尾不加句号或任何点号。

**完美示例：**
- `feat(auth): 新增微信扫码登录逻辑`
- `fix(ui): 修复导航栏在移动端重叠的显示异常`
- `refactor(api): 抽离统一的 axios 错误拦截器`

## 2. 提交前的代码自查 (Sanity Check)

在最终执行提交操作前，代理(Agent)必须确认以下事项：
1. **脏代码清理**：利用 `git diff` 查验是否误留了为了调试而写的 `console.log`、`debugger`，亦或是提交了敏感账号配置等不该包含的临时文件。
2. **JSDoc 类型防线**：虽然本项目使用的是 JavaScript，但对于处理复杂业务流的核心模块，请在提交前补齐标准的 `JSDoc` 函数签名与参数类型提示。
